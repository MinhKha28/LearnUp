# UC25.4 backend — API, verification and demo handoff

## API contract

Responses use the existing learning-service envelope (`statusCode`, `message`, `data`); errors use the existing `error` envelope.

| Method and path | Access / input | Result |
| --- | --- | --- |
| `POST /api/v1/enrollments/:enrollmentId/withdrawal` | Learner, no body; scoped to enrollment ID, learner ID and organization ID | 200 `data: { outcome: 'DELETED' \| 'WITHDRAWN' }` |
| `POST /api/v1/enrollments` | Learner; `{ courseId: UUID }`; existing rate limit, Subscription and Published/Public checks | 201 `data: { id, courseId, enrollmentType, status, enrolledAt, restored: boolean }` |

| Status / code | Extra fields / meaning |
| --- | --- |
| 404 `ENROLLMENT_NOT_FOUND` | Missing, another learner/organization, already withdrawn or invalid enrollment ID |
| 409 `ENROLLMENT_NOT_WITHDRAWABLE` | `reason: 'REQUIRED' \| 'COMPLETED'`; checked before assessment and again after row lock |
| 503 `ASSESSMENT_UNAVAILABLE` | Network, timeout, non-success HTTP or invalid assessment response; no learning DB mutation |
| 409 `ENROLLMENT_NOT_RESTORABLE` | `reason: 'AccountDeleted' \| 'HaltedClosed'`; checked locally before Subscription/I1, and again under row lock |
| 409 `ALREADY_ENROLLED` | Existing active enrollment or concurrent restoration loser; includes `enrollmentId` |

`LearnerWithdrew` outbox uses `aggregateType: 'Enrollment'`, `aggregateId: enrollmentId`, `organizationId`, and `occurredAt: withdrawnAt`. Payload: `{ enrollmentId, learnerId, organizationId, courseId, withdrawnAt }`, with an ISO timestamp. Delete branch emits no event. Both branches keep the version snapshot and Course Locked state.

Restore reuses the same row, clears `withdrawn_at`/`withdrawn_reason`, preserves material progress and `video_completion_percent`, and evaluates the shared SQL expression: `first_activity_at IS NULL → NotStarted`, otherwise `InProgress`. UC24.2 behavior is unchanged: it does not inspect `withdrawn_reason`; its existing learner/account/type/course checks still apply.

## Assessment contract for Danh

Client only; the endpoint is proposed and is not implemented by this branch in assessment-service.

```http
GET /api/v1/internal/learners/:learnerId/courses/:courseId/assessment-activity
x-internal-key: <INTERNAL_SERVICE_KEY>
x-user-id: <caller learner UUID>
x-user-role: LEARNER
x-organization-id: <organization UUID>
```

`courseId` identifies the version. Expected 200 JSON:

```json
{"data":{"hasQuizAttempt":false,"hasSubmission":false,"hasPeerReviewGiven":false}}
```

All three fields must be booleans. Any true means assessment activity exists; a quiz attempt counts from its start. HTTP failures never mean no activity.

Configuration: `ASSESSMENT_CLIENT_MODE=fake|http`. Fake refuses production, validates every UUID in comma-separated `ASSESSMENT_FAKE_RESULT_COURSE_IDS` at startup, and sets all three flags true for listed versions. HTTP requires `ASSESSMENT_SERVICE_URL`, `INTERNAL_SERVICE_KEY`; `ASSESSMENT_SERVICE_TIMEOUT_MS` defaults to 3000. The sample configuration is in `services/learning-service/.env.example`.

## EXPLAIN (ANALYZE, BUFFERS)

Fixture: 50,001 enrollments, with one material progress row and one status interval per enrollment. All data belongs to the existing integration fixture organization. Each measured mutation rolls back; suite cleanup removes the fixture. The integration test checks root plans and captures actual nested CASCADE plans using `auto_explain`, including buffers and timing. Full captured plans are in [uc25.4.explain.json](uc25.4.explain.json).

| Query | Scan / index | Execution time, ms |
| --- | --- | ---: |
| `SELECT ... FOR UPDATE` | Index Scan, `enrollments_id_organization_id_key` | 0.158 |
| Delete enrollment including CASCADE | Index Scan, `enrollments_id_organization_id_key` | 0.964 |
| Update Withdrawn | Index Scan, `enrollments_id_organization_id_key` | 0.320 |
| Restore | Index Scan, `enrollments_id_organization_id_key` | 0.330 |
| Local owned enrollment lookup | Index Scan, `enrollments_id_organization_id_key` | 0.131 |
| Registration lookup | Index Scan, `enrollments_learner_id_course_id_key` | 0.136 |
| Nested CASCADE status intervals | Index Scan, `enrollment_status_intervals_enrollment_id_kind_started_at_key` | 0.019* |
| Nested CASCADE material progress | Index Scan, `material_progress_enrollment_id_material_id_key` | 0.016* |

*Nested timings are the DELETE plan node's actual total time, not a separate top-level execution time. No child Seq Scan was observed. Times describe this fixture run, not a production latency target.

Existing test updated: `EXPLAIN ANALYZE BUFFERS lock and updates on 50000 enrollments use primary key` in `test/integration/assignment-changes.integration-test.ts`. PostgreSQL chose `enrollments_id_organization_id_key` for its lock, due-date update and exemption update. Its `(id, organization_id)` key directly matches both equality predicates and is unique, so it identifies at most one enrollment. The assertion now accepts exactly that named Index Scan; it does not accept arbitrary indexes.
